# OpenRig v0.5.10 — explainable System Health

OpenRig 0.5.10 makes fleet health inspectable without turning observation into
another source of work. Agents and operators can query the same bounded,
evidence-bearing findings in the CLI and TUI, hand uncertain patterns to an
agent for diagnosis, and route a verified human request when project policy
requires it. The release also carries authored mission context through workflow
waits, so lifecycle progress no longer depends on an orchestrator remembering
the ceremony.

## System Health

- **Inspect health at the scope you actually own.** `rig health` supports the
  current seat, a stable seat ID, a rig, or the local instance. Each finding
  retains its category, severity, status, confidence, source window, freshness,
  rule, evidence, policy version, and smallest useful next inspection. Empty
  output explicitly does not claim health.
- **See the same truth in the terminal UI.** Instance, rig, and seat views expose
  compact health summaries, a HEALTH list, and finding drill-in from the same
  canonical records used by the CLI. There is no second score or TUI-only health
  authority.
- **Detect high-confidence operational failures without transcript sentiment.**
  Deterministic detectors cover process, governance, and context signals such as
  queue amplification, authority-boundary traffic, and context pressure. Stable
  episode identity, source bounds, freshness, and explicit indeterminate states
  prevent missing or stale evidence from reading as healthy.
- **Ask an agent to diagnose the cases code cannot settle.** Opt-in health policy
  can present one bounded investigation packet for ceremony amplification. The
  assigned agent may inspect beyond the packet, record an attributed disposition,
  and request human notification only under configured policy and connector
  readiness. Diagnosis traffic is excluded from its own detector input.

## Durable lifecycle and human delivery

- **Carry authored mission context through workflow waits.** A mission can select
  an explicit boundary workflow in `mission.yaml`; compilation includes the
  project and mission manifests plus declared context references. Waiting steps
  can re-present the same packet with bounded exponential backoff, preserving one
  obligation rather than manufacturing replacement rows.
- **Select SDLC care from authored components and waves.** Shipped role and pod
  guidance follows the project and mission selection instead of inferring a
  builder-to-QA-to-review chain from seat names. Role capacity does not create a
  gate.
- **Address humans through registered delivery channels.** Registered
  `<entityId>@external` addresses expose readiness and a next inspection. A
  verified queue create persists the request before checking its receipt, while
  posted, pending, failed, and indeterminate outcomes remain distinct. Direct
  replies return through the correlated queue thread instead of being rewritten
  as terminal input.

## Upgrade and setup notes

- Root, CLI, daemon, and web UI package versions advance to `0.5.10`. The
  terminal TUI keeps its independent `0.1.0` version.
- This release adds no database migration beyond the `0.5.9` migration head.
  Normal daemon restart is sufficient for schema state; runtime adoption remains
  a separate operator decision.
- Health list and explain are read-only. Automated diagnosis is disabled until a
  policy explicitly enables it, and no detector automatically retries, reroutes,
  relaunches, edits scope, or changes lifecycle state.
- Human delivery requires a registered address and a configured, enabled, ready
  connector. Connector setup or verification does not itself send a message.

## Known limitations

- Deterministic shipped detector domains are process, governance, and context.
  Behavioral and epistemic conclusions remain attributed agent judgment rather
  than opaque scoring.
- System Health observes bounded retained records. Unsupported, clipped, stale,
  contradictory, or unavailable inputs stay indeterminate; absence of a finding
  is not proof that the system is healthy.
- Mission-boundary workflows carry context and scheduling, but agents retain the
  judgment about evidence, publication, and activation. The daemon does not
  interpret Markdown receipts or invent the next mission.
- Slack is one human-delivery connector, not the addressing contract, and a
  posted receipt proves connector acceptance rather than human readership.
